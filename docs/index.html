A terminal you can drop on a form.

A control for Avalonia that is a real terminal: it parses what a program prints, draws the screen, and sends back what the user types. It brings its own shell, so it works on a machine where nobody has installed zsh — and it works with no shell at all, if what is on the far end is an SSH channel or an interpreter in your own process.

Install the package dotnet add package AvaTerminal --prerelease
Put one on a form <ava:AvaTerminal />

This is a preview. The parser, the renderer and the shell work; the API may still move before 12.1.0 final.

The demo is the documentation, running

Every panel in it is a property or an event from these pages: the font, the theme, the console size, what to run, what to send, what to feed, and a log of everything the control raises. Open it in your browser — it needs nothing installed.

A browser tab has no pty, so the hosted demo runs the library's documented "terminal with no process" mode: AutoStart="False", and a shell written in about two hundred lines of the demo answering Input with Feed. The parser, the renderer and the input encoding on that page are the real ones. Run the same demo on your machine — dotnet run --project demo/AvaTerminal.Demo.Desktop — and the session picker gains the built-in shell, your login shell, and top on a real pty.

What is in the box

A VT/xterm parser

CSI, OSC, DCS and SGR. The alternate screen, scrollback, wide characters and combining marks, and reflow when the console is resized. Written here rather than wrapped: there is no libvterm and no xterm.js in the package.

A cell renderer

Glyph runs through Avalonia's own drawing context, snapped to whole device pixels so column boundaries do not land on a third of one. Dirty-region repaints, and a cursor that blinks at xterm's 530 ms.

Keyboard and mouse

Application cursor keys, bracketed paste, mouse modes 1000/1002/1006. Text goes through the platform's own input path, so a dead key or an IME composition arrives as the character the user meant rather than as the keys they pressed.

A pty per program

posix_openpt and posix_spawn behind an interface. A program asks the kernel whether it is on a terminal and gets the answer it needs — which is the difference between running ls and running vim.

A shell of its own

cd, pwd, exit and help are builtins; everything else is a file found on PATH. No zsh, no bash, no cmd.exe — nothing installed.

Or no process at all

Turn AutoStart off and nothing is spawned and no pty is opened. Feed it bytes, handle the bytes it emits, and you have a terminal over an SSH channel, a container, a serial port or a replayed recording.

Three ways to use it

1 · A shell, with nothing installed

Content = new AvaTerminal();

The built-in shell starts, sized to whatever rectangle the control is given. Type ls and you get /bin/ls.

2 · A program

var terminal = new AvaTerminal();
terminal.Start("/usr/bin/ssh", ["build-host"]);
terminal.Exited += code => Close();

An absolute path and its arguments — there is no shell parsing here, and no PATH search, because a control that split its own command line would be a second, worse shell.

3 · Whatever you like, over anything

var terminal = new AvaTerminal { AutoStart = false };   // spawns nothing, opens no pty

terminal.Input += bytes => channel.Send(bytes);         // what the user typed
channel.Received += bytes => terminal.Feed(bytes);      // what the far end printed

This is the mode with no platform in it. Starting a program is the only thing that needs a pty, so a terminal that starts nothing never reaches that code.

What it deliberately is not

Not a terminal application

No chrome, tabs, splitting, search or session manager. It is a terminal in a rectangle; everything around it belongs to the application it is dropped into.

Its shell is not zsh

No pipes, redirection, globbing, variables or job control. Each of those is a language feature, and a half-implementation that silently ignored > out.txt would be worse than an honest absence. StartSystemShell() runs the user's own.

Not Windows yet

macOS and Linux. The pty layer is posix_spawn and openpty; Windows needs a ConPTY implementation of IPtyHost, which is one class and no change above it.

Not a font rasteriser

The library decides which glyph goes in which cell at which pixel, with fallback-font resolution and device-pixel snapping. Avalonia turns the outline into pixels — that part is not ours, and nobody writes it twice.
