Troubleshooting

A terminal in your application

This assumes you have written an Avalonia application and have never written a terminal. It takes about ten minutes, and the first step is one line.

Put one on a form

dotnet add package AvaTerminal --prerelease

In XAML:

<Window xmlns="https://github.com/avaloniaui"
        xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
        xmlns:ava="clr-namespace:AvaTerminal;assembly=AvaTerminal"
        x:Class="MyApp.MainWindow"
        Width="900" Height="560">
    <ava:AvaTerminal />
</Window>

Or from code, which is the same thing:

using AvaTerminal;

public class MainWindow : Window
{
    public MainWindow()
    {
        Width = 900;
        Height = 560;
        Content = new AvaTerminal();
    }
}

Run it. You have a terminal: type ls and press Return, and you will get a directory listing. Type vim and you will get vim.

Nothing was installed and nothing was configured. In particular no zsh, no bash and no cmd.exe is involved — see the next step for what actually ran ls.

What just happened

Worth two minutes, because "terminal" is used for three different things and knowing which is which makes the rest of this guide obvious rather than magic.

What it isWhose
a pty A kernel object — a pipe with terminal semantics: echo, line editing, Ctrl-C to SIGINT, a window size. It renders nothing and parses nothing. the kernel's
a shell An ordinary interactive program that turns a typed line into a running one. Not a terminal, and — here — optional. BuiltinShell, or one you name
a terminal emulator Parses the byte stream into a screen, draws that screen, and encodes keystrokes back into bytes. AvaTerminal

So when you typed ls: the control's shell read the line, searched PATH for a file called ls, found /bin/ls, opened a pty, started that program on it, and fed everything the program printed into the parser. The parser turned the bytes into cells; the renderer drew them.

ls is 150 KB of somebody else's program. No shell anywhere has it built in, and neither does this one.

Run a program instead

Most applications embedding a terminal do not want a shell at all. They want one program.

var terminal = new AvaTerminal();
terminal.Start("/usr/bin/ssh", ["build-host"]);

or, entirely in XAML:

<ava:AvaTerminal Command="/usr/bin/top" WorkingDirectory="/src/app" />
Command is an absolute path. There is no PATH search here and no shell parsing: a control that split its own command line would be a second, worse shell. If you have a name rather than a path, ask for the path: 
if (CommandResolver.TryResolve("git", null, out var path, out var why))
    terminal.Start(path, ["log", "--oneline"]);
else
    ShowError(why);

If you want the user's own shell — their aliases, their prompt, their completion — ask for it by name: 

terminal.StartSystemShell();     // $SHELL, or /bin/sh

Give it a size

By default the console follows the control: make the window bigger and the program is told it has more room. That is what you want for a terminal that is the window.

Sometimes it is not. A fixed-format report, a transcript, a widget in a panel:

<ava:AvaTerminal AutoSize="False" Columns="80" Rows="24" />

Now the console is 80x24 whatever the control's rectangle turns out to be. Writing to Columns or Rows is what turns the fitting off — the property is both the question and the answer.

Read them at any time to find out what the console currently is: 

terminal.ScreenChanged += () =>
    status.Text = $"{terminal.Columns}x{terminal.Rows}";

Make it look right

The font

terminal.Font = TerminalFont.Resolve("JetBrains Mono", "Fira Code", "Menlo");
terminal.TerminalFontSize = 13;

The first family that is actually installed wins; if none are, it falls back through a built-in list ending somewhere every platform has. A cell is measured from the face's own metrics and snapped to a whole device pixel — that snapping is why a wall of text has no grey seams in it.

The colours

terminal.TerminalTheme = Theme.Dark;   // the default: xterm's own sixteen colours

Or build one. The sixteen ANSI colours are yours; the other 240 are computed from the standard cube and grey ramp. 

var ansi = new Rgba[16] { /* ... */ };

terminal.TerminalTheme = new Theme(
    foreground:   Rgba.FromHex(0xE4E4E4),
    background:   Rgba.FromHex(0x101216),
    cursor:       Rgba.FromHex(0x7FD8A0),
    cursorText:   Rgba.FromHex(0x101216),
    selection:    Rgba.FromHex(0x2E4A6B),
    ansi16:       ansi,
    boldIsBright: true,
    dimAmount:    0.45);
Leave Background alone unless you mean it. It defaults to null, which means "the theme's background" — set it and you have overridden the theme for that one colour.

Talk to it from code

Type into it

terminal.Send("git status\r");        // \r is Return

Put something on the screen without sending it

terminal.Feed("\u001b[33mwarning:\u001b[0m nothing is running\r\n"u8);

Watch what the user types

terminal.Input += bytes => recorder.Write(bytes.Span);

Send deliberately does not raise Input. If it did, an application that broadcast one terminal's input to the others would have written a loop.

Interrupt it

terminal.Signal(PtySignal.Int);       // what Ctrl-C does
terminal.Signal(PtySignal.Term);      // ask it to stop
terminal.Stop();                      // end it now

Know what it is doing

terminal.Exited        += code  => status.Text = $"exited with {code}";
terminal.TitleChanged  += title => tab.Header  = title;
terminal.Bell          += ()    => tab.Flash();
terminal.ScreenChanged += ()    => UpdateStatusBar();

Exited arrives after the program's last output, and after the control has torn down: IsRunning is already false when your handler runs. That ordering is the half worth relying on — the last thing a program prints is regularly the thing the user needs.

And you can read the screen at any time:

var screen = terminal.Screen;

if (screen.IsAlternateScreen)         // vim or top is up
    HideTheFindBar();

var text = screen.GetScreenText();    // everything visible
The screen is a model, not a transcript. A program that redraws a progress bar ten thousand times leaves one row. If you want a transcript, record what you fed it.

A terminal with no process

This is the step worth reading even if you skipped the rest. AvaTerminal is the terminal — a screen and a keyboard. Pointing it at a local program is optional. 

var terminal = new AvaTerminal { AutoStart = false };   // spawns nothing, opens no pty

terminal.Input    += bytes => channel.Send(bytes);      // what the user typed
channel.Received  += bytes => terminal.Feed(bytes);     // what the far end printed

Six lines, and that is a complete terminal over an SSH channel, a Docker exec stream, a serial port, a WebSocket, a recording being replayed — or an interpreter running in the same process.

It is also the mode with no platform in it: starting a program is the one thing that needs a pty, so a terminal that starts nothing never reaches that code.

Answers are handled for you. When the far end asks the terminal a question — "where is the cursor", "what are you" — the answer comes out through Input along with the keystrokes, so forwarding Input forwards a complete terminal.

Scenarios

Five things people actually build with this, in the shortest form that works.

A build output pane

A read-only terminal that shows a compiler's output, in colour, with its progress bars working — which is the whole reason to use a terminal rather than a TextBox. 

var output = new AvaTerminal
{
    AutoStart = false,          // nothing runs until the user presses Build
    IsHitTestVisible = false,   // read-only: no keyboard, no mouse reporting
};

async Task BuildAsync()
{
    output.Stop();
    output.Feed("\u001b[2J\u001b[H"u8);            // clear, home

    if (!CommandResolver.TryResolve("dotnet", projectDirectory, out var path, out var why))
    {
        output.Feed(Encoding.UTF8.GetBytes($"{why}\r\n"));
        return;
    }

    var done = new TaskCompletionSource<int>();
    output.Exited += code => done.TrySetResult(code);
    output.Start(path, ["build", "-c", "Release"], projectDirectory);

    ExitCode = await done.Task;
}
A pty is what makes this worth doing. dotnet build, cargo, npm and make all ask the kernel whether their output is a terminal, and give you colour and progress only when it is. Piping them into a text box gets you the plain, dull version.

An SSH client

Two ways, and the first one is usually the right one.

Run the system's ssh

terminal.Start("/usr/bin/ssh", ["-t", "user@host"]);

Everything works, including the parts nobody wants to reimplement: keys, agents, ~/.ssh/config, jump hosts, host key prompts. The terminal is local and the pty is local; ssh deals with the far end.

Or hold the connection yourself

var terminal = new AvaTerminal { AutoStart = false };

var stream = await sshClient.OpenShellAsync(
    columns: terminal.Columns, rows: terminal.Rows);

terminal.Input += bytes => stream.Write(bytes.Span);

_ = Task.Run(async () =>
{
    var buffer = new byte[16 * 1024];
    int n;
    while ((n = await stream.ReadAsync(buffer)) > 0)
    {
        var chunk = buffer[..n];
        await Dispatcher.UIThread.InvokeAsync(() => terminal.Feed(chunk));
    }
});

// and tell the far end when the window changes
terminal.ScreenChanged += () => stream.SetSize(terminal.Columns, terminal.Rows);
Feed on the UI thread. The control is an Avalonia control; a read loop on a background thread has to marshal. The local pty path does this for you — a channel you own does not.

Your own REPL, in your own process

No pty, no child process, nothing to install. The terminal is a screen and a keyboard, and you are the program. 

var terminal = new AvaTerminal { AutoStart = false };
var line = new StringBuilder();

terminal.Feed("Type an expression.\r\n> "u8);

terminal.Input += bytes =>
{
    foreach (var b in bytes.Span)
    {
        switch (b)
        {
            case 0x0d:                                   // Return
                terminal.Feed("\r\n"u8);
                var answer = Evaluate(line.ToString());
                terminal.Feed(Encoding.UTF8.GetBytes($"{answer}\r\n> "));
                line.Clear();
                break;

            case 0x7f when line.Length > 0:              // Backspace
                line.Length--;
                terminal.Feed("\b \b"u8);
                break;

            case >= 0x20:
                line.Append((char)b);
                terminal.Feed([b]);                      // echo
                break;
        }
    }
};

The escape sequences all work, because the engine is real: colour the answers with ESC [ 32 m, clear with ESC [ 2 J, draw a full-screen view on the alternate screen with ESC [ ? 1049 h. samples/AvaTerminal.Hosted is this scenario, finished.

A byte is not a character. The sketch above appends (char)b, which is right only for ASCII — anything else arrives as two to four bytes of UTF-8. Decode with a stateful Encoding.UTF8.GetDecoder(), because the halves of one keystroke can arrive in separate calls.

Running an agent, or any long-lived TUI

A coding agent, htop, lazygit — programs that draw a full screen, want every keystroke, and run for hours. 

var terminal = new AvaTerminal();
terminal.Start(agentPath, ["--project", projectDirectory], projectDirectory);

// A full-screen program is up: the application's own shortcuts should get out of the way.
terminal.ScreenChanged += () =>
{
    var fullScreen = terminal.Screen.IsAlternateScreen;
    findShortcut.IsEnabled = !fullScreen;
};

// It says what it is doing in the title.
terminal.TitleChanged += title => tab.Header = title;

// And it rings the bell when it wants you.
terminal.Bell += () => tab.NeedsAttention = true;
Do not resize it casually. On the alternate screen there is no scrollback to restore from, so a shrink and re-grow destroys content permanently. If your layout moves a lot — a panel that collapses, a sidebar that slides — pin the size with AutoSize="False" and let the control letterbox the console instead.

Many terminals

var tabs = new TabControl();

void AddTerminal(string title)
{
    var terminal = new AvaTerminal();
    var item = new TabItem { Header = title, Content = terminal };

    terminal.TitleChanged += t => item.Header = t;
    terminal.Exited += _ => tabs.Items.Remove(item);

    tabs.Items.Add(item);
}

Each control owns its own screen, its own process and its own cursor blink; nothing is shared between them. Closing a tab takes the control out of the visual tree, which stops the process and releases the screen — an application that opens and closes fifty tabs costs fifty terminals while they are open and none afterwards.

A TabControl that recycles the content of an unselected tab would detach the control and stop the program. Either keep the controls alive yourself and swap them into a ContentControl, or make sure the tab hides its content rather than detaching it.

Troubleshooting

Nothing happens when I type

The control needs the keyboard. It is Focusable, but something has to give it focus: click it, or call terminal.Focus() once the window is shown.

The program says the terminal is too small, or draws off the edge

Read terminal.Columns and terminal.Rows — that is what the program was told. If you are driving a remote channel yourself, you have to forward the size when it changes; the local pty path does it for you.

Start throws PtyException

Command is an absolute path. Use CommandResolver.TryResolve to turn a name into one, or use the built-in shell, which does that itself.

Colours are wrong in one program

Check whether it is deciding based on TERM. If a program wants something specific, pass it: 

terminal.Start(path, args, cwd,
    new Dictionary<string, string> { ["TERM"] = "xterm-256color" });

It does not build on Windows

It does not run on Windows yet. The pty layer is posix_spawn and openpty; Windows needs a ConPTY implementation of IPtyHost, which is one class and no change above it. The parser, the renderer and the input encoding are already platform-free.
