Install

dotnet add package AvaTerminal --prerelease

One package, one assembly, one dependency (Avalonia). Requires Avalonia 12.1 and .NET 8.0 or later, on macOS or Linux. 

using AvaTerminal;

In XAML, the control is in the assembly's own namespace: 

<Window xmlns:ava="clr-namespace:AvaTerminal;assembly=AvaTerminal">
    <ava:AvaTerminal />
</Window>

AvaTerminal

An Avalonia Control. It owns a pty, a VT engine that parses what comes back, and a scene of exactly one terminal.

A bare control starts the built-in shell when it is attached to a visual tree. Everything below is optional.

Properties

All of these are Avalonia StyledProperty, so they can be set in XAML, bound, or given a value by a style.

PropertyTypeDefault
Commandstring?null The program to run — an absolute path. There is no PATH search and no shell parsing here: a control that split its own command line would be a second, worse shell. null runs the built-in shell.
ArgumentsIReadOnlyList<string>[] Arguments for Command, excluding the program name itself.
WorkingDirectorystring?null Where the program starts. null leaves it to the process the control is in.
AutoStartbooltrue Whether attaching to a visual tree starts anything at all. false is the mode with no process and no pty.
AutoSizebooltrue Whether the console follows the control's rectangle. See Sizing.
Columns / Rowsint120 / 40 The console size. Read them to find out what it is; writing either one pins the size and turns AutoSize off for good.
TerminalFontSizedouble14 In device-independent pixels. Changing it re-measures the cell and re-fits the console.
BackgroundIBrush?null What is painted behind the screen. null means the theme's background — so a style, or a different TerminalTheme, actually takes effect.
Changing what to run restarts it. Command, Arguments and WorkingDirectory are one decision written on three lines, so setting any of them while something is running restarts it — once, after the current dispatcher turn, so three assignments in a row are one restart with all three values.

Events

public event Action<int>? Exited;

The program ended, with its exit code — after its last output. The ordering is the half worth relying on: the last thing a program prints is regularly the thing the user needs, and a control told about the exit first would be free to tear the screen down before it arrived. By the time this is raised IsRunning is already false.

public event Action? ScreenChanged;

Anything at all was drawn. Raised on every chunk of output and on every Feed.

public event Action<string>? TitleChanged;

The program set the window title. What a shell prompt uses to say which directory it is in, and what ssh, vim and top use to say what they are. An application with tabs puts it on the tab.

public event Action? Bell;

The program rang the bell (0x07). Deliberately not turned into a sound: whether a bell is audible, a flash, a dock badge or nothing at all is a decision about the application, and a library that made it would be a library that beeps in a build log viewer.

public event Action<ReadOnlyMemory<byte>>? Input;

The bytes the user's keystrokes and mouse gestures encode to — and the bytes the terminal emits when it answers a question the program asked. Raised whether or not anything is running, and after the running program has been written to.

This is the other half of Feed, and what makes the control usable with no process behind it: send these wherever the far end is, and push what comes back through Feed.

Send deliberately does not raise this. An application that broadcasts Input to its other terminals with Send would otherwise have written a loop.

Methods

public void Start(string command, IReadOnlyList<string>? arguments = null, string? workingDirectory = null, IReadOnlyDictionary<string, string>? environment = null)

Starts a program, replacing whatever was running. command is an absolute path; environment is added to what the process inherits.

public void StartBuiltinShell(string? workingDirectory = null)

Starts the shell that comes with the control — the default, and what needs no other program. See BuiltinShell.

public void StartSystemShell(string? workingDirectory = null)

Starts $SHELL, or /bin/sh. The choice every other terminal emulator makes, and here for an application that wants the user's own shell with their aliases, prompt and completion.

public void Stop()

Ends whatever is running. Does nothing when nothing is. Called automatically when the control leaves the visual tree.

public void Send(string text) public void Send(ReadOnlyMemory<byte> data)

Types into whatever is running — a program on the pty, or the built-in shell. The string overload is UTF-8 encoded; append "\r" to press Return.

public void Feed(ReadOnlySpan<byte> data)

Puts bytes on the screen as though the program had printed them, and sends nothing. The seam for a terminal that is not driven by a local process: an ssh channel, a container, a recording being replayed.

public void Signal(PtySignal signal)

Signals the program's process group. PtySignal.Int is Ctrl-C's path; Hup, Quit, Kill, Term, Cont, Stop, Tstp, Winch, Usr1 and Usr2 are the rest. Under the built-in shell it reaches the program the shell is running, and at its prompt an interrupt means what Ctrl-C means there: abandon the line.

Sizing

The console is resized to fit the control, and resizing the window resizes the program. That is AutoSize, and it is on by default because a terminal dropped on a form is the window.

Setting Columns or Rows pins the size instead — the property is both the question and the answer, so writing to it is what turns the fitting off — and the control then draws that console inside whatever space it has. 

<ava:AvaTerminal AutoSize="False" Columns="80" Rows="24" />

An unconstrained control asks for exactly its console, so a terminal in a StackPanel or a SizeToContent window is Columns × Rows of the face it draws in rather than nothing at all.

Whole cells only. Half a column is not a column, and a program told it has one would draw into pixels that are not there. A rectangle that fits 40.9 columns is a console of 40.
A resize to the size it already has signals nothing. A layout pass that produced the same answer must not raise SIGWINCH: a full-screen program redraws on every one, and a control is arranged far more often than it is resized.

Appearance

Font

TerminalFont.Resolve(params string[] families) picks the first monospaced family that is actually installed, falling back through a built-in list that ends somewhere every platform has. 

terminal.Font = TerminalFont.Resolve("JetBrains Mono", "Menlo");
terminal.TerminalFontSize = 13;

A cell is measured from the face's own advance width and line spacing, then snapped to a whole device pixel — column boundaries on a third of a pixel are what makes a grid of text look like it has grey seams in it.

Colours

Theme is the terminal's colour model: the 256-entry palette, what "default" means, and how the rendition attributes that are colour decisions — bold, dim, reverse, invisible — change the answer. 

terminal.TerminalTheme = new Theme(
    foreground:  Rgba.FromHex(0xE4E4E4),
    background:  Rgba.FromHex(0x101216),
    cursor:      Rgba.FromHex(0x7FD8A0),
    cursorText:  Rgba.FromHex(0x101216),
    selection:   Rgba.FromHex(0x2E4A6B),
    ansi16:      myPalette,      // exactly 16
    boldIsBright: true,          // SGR 1 promotes 0-7 to 8-15, as xterm does
    dimAmount:    0.45);

Theme.Dark is the default and uses xterm's own sixteen colours verbatim — worth using rather than something prettier, because every program that picks colour 2 was written and looked at against roughly these.

Changing the theme re-colours a screen that was painted an hour ago: the engine stores what the program said (palette index 4), never what it should look like.

BuiltinShell

The shell the control runs when you have not given it a Command. It finds the program you named, runs it, and shows what it printed.

A shell is two things and no more. A handful of builtins that have to run inside it — cd is the whole argument, since a separate process cannot change its parent's directory — and for everything else, a search of PATH for a file of that name, then run it.

Builtin
cd [dir]Changes the shell's directory. ~ is expanded; no argument means home. This is the one that has to be a builtin — a separate process cannot change its parent's directory.
pwdPrints it.
export NAME=valueSets a variable for the programs this shell runs. With no arguments, lists what has been set.
unset NAMETakes it away again.
which NAMEWhere that command would come from — the shell's own PATH search, made visible.
type NAMEThe same, and says when a name is a builtin rather than a file.
historyThe lines you have run. The up arrow walks the same list.
clearErases the screen.
exitEnds the shell, which raises Exited(0) on the control.
helpLists all ten, and what is deliberately missing.
Everything else is a program on disk. mkdir, rm, cp, mv, grep, find, git, python — none of these are commands anywhere. They are files in /bin and /usr/bin, and the shell finds them on PATH and runs them. There is nothing to add to this shell to make them work.

Patterns

ls *.txt does not hand ls a pattern: the shell replaces the word with every matching name before the program starts. That is why every program on the system understands patterns without knowing what one is.

* and ?Expanded in the last segment of a path.
"*.txt"Quoted, so not expanded — which is how you name a file that really is called that.
no matchThe word is passed through as it was typed, as bash does. The program then reports the name it was given.
.hiddenA leading dot is not matched by a pattern that does not have one — the reason rm * does not take your configuration with it.
not implementedCharacter classes ([a-z]), **, and patterns in the directory part.
Key
ReturnRuns the line.
BackspaceRemoves one character — an emoji goes in one press, not two.
Up / DownHistory, 500 lines deep.
Ctrl-CAt the prompt, abandons the line. While a program is running it is the pty's, and becomes SIGINT.
Ctrl-DOn an empty line, ends the shell. Anywhere else it means end-of-input to the program.
What it is not. There are no pipes, no redirection, no $variables, no &&, no job control and no scripting. Each of those is a language feature, and a shell that has them is a shell somebody spent years on. Quoting is handled — cd "My Documents" works — because a line copied out of a terminal has to mean here what it meant there.

Every program runs on a pty of its own, which is what makes vim, top and git log work rather than only ls: a program asks the kernel whether its output is a terminal and behaves completely differently either way, and only a pty answers yes.

A non-zero exit status is reported, because the program may have printed nothing at all and "it did nothing" is the least useful thing a terminal can say. Zero is silent.

Using it directly

You rarely need to — the control creates one for you — but it is public, and it is where you would start if you wanted a shell without a screen. 

var shell = new BuiltinShell(
    output: data => terminal.Feed(data.Span),   // where what it prints goes
    size:   () => new ConsoleSize(80, 24),      // asked when a program starts
    post:   Dispatcher.UIThread.Post,           // how it reaches the screen's thread
    workingDirectory: "/src/app");

shell.Exited += () => Close();
shell.Start();
shell.Input("ls\r"u8.ToArray());
WorkingDirectoryWhere commands run. Changed by cd and by nothing else.
IsBusyWhether a program is running, and therefore where the keyboard is going.
PidThat program's process id, or null at the prompt.
Resize(ConsoleSize)Tells a running program the console changed size.
Signal(PtySignal)Signals it, or ends the line being typed when there is none.

PtyTerminalSession

One program on one pty: a background read loop, and the writes, resizes and signals that go the other way. 

await using var session = PtyTerminalSession.Start(
    new PtyStartInfo
    {
        Command = "/bin/sh",
        Args    = ["-c", "echo hello; sleep 5"],
        Size    = new ConsoleSize(80, 24),
    },
    post: Dispatcher.UIThread.Post);

session.Output += chunk => terminal.Feed(chunk.Span);
session.Exited += code => Console.WriteLine($"exit {code}");
session.Run();

post is how the reader thread reaches the thread that owns the screen. Everything raised — Output and Exited — arrives through it, so a handler never has to think about which thread it is on.

Pid, Size, HasExitedWhat it is.
Run()Starts the read loop. Idempotent.
Write(ReadOnlyMemory<byte>)To the program.
Resize(ConsoleSize)Sets the kernel's idea of the size and raises SIGWINCH. A resize to the size it already has does nothing at all.
Signal(PtySignal)To the foreground process group.
DisposeAsync()Ends the process. A terminal that went away leaving a process behind is a process nobody can see, type into or find.

Reading the screen

terminal.Screen is the VtEngine: the parsed state, not a byte log. 

var screen = terminal.Screen;

screen.GetScreenText();                  // everything visible, as text
screen.Columns, screen.Rows;             // the console size
screen.CursorX, screen.CursorY;          // where the cursor is
screen.IsAlternateScreen;                // true while vim or top is up
screen.Title;                            // what OSC 0 last set
screen.Scrollback;                       // what has gone off the top

var line = new StringBuilder();
screen.AppendRowText(line, screen.ActiveScreen[0]);   // one row

The engine also raises the things a terminal is told rather than shown, which the control forwards where they are worth forwarding:

TitleChangedOSC 0 / OSC 2 — forwarded as AvaTerminal.TitleChanged.
BellBEL — forwarded as AvaTerminal.Bell.
ReplyThe terminal's answer to a question. Handled for you: it goes back to the program exactly as a keystroke does. Do not also forward it, or the program is answered twice.
NotificationRequestedOSC 9 / OSC 777 desktop notifications.
PromptMarkedOSC 133 shell integration marks — where a prompt began, where a command's output began, and what it exited with.
ClipboardRequestedOSC 52. Not acted on by the control; a program that can write your clipboard is a decision for the application to make.
AlternateScreenChangedA full-screen program came up, or went away.
The screen is a model, not a transcript. A program that redraws a progress bar ten thousand times leaves one row, not ten thousand. If you want a transcript, record what you fed it.

CommandResolver

The PATH search, on its own, for an application that wants to find a program without running one — to grey out a button, or to say why something is missing before the user waits for it.

public static bool TryResolve(string? command, string? workingDirectory, out string? path, out string? error, string? environmentPath = null)

A name containing a separator is a path and is never searched for — the rule that makes ./build run the one in this directory rather than one that happens to be on PATH under the same name. A bare name is looked for in each directory of PATH in turn, and a file that is present but not executable is skipped rather than reported: PATH directories hold data files too, and stopping at the first matching name sends the user looking in the wrong place.

CommandLine.TrySplit is the other half — a shell's quoting rules and nothing past them, so a line copied out of a terminal means here what it meant there.

Threading and lifetime

The ruleWhy
Call the control from the UI thread. It is an Avalonia Control. Output arriving from a pty is already marshalled for you.
The process goes with the control. Leaving the visual tree calls Stop(). A terminal taken off screen with a shell still running on it is a process nobody can see, type into or find.
Detaching releases the screen. An application that opens and closes fifty terminal tabs costs fifty terminals' worth of memory while they are open, and none afterwards.
Re-attaching works. A control moved from one parent to another comes back with its screen intact. It does not restart what was running, because it stopped it — start it again if you want it.
Two controls are independent. Each owns its scene, its engine and its cursor blink. Nothing is shared between them.

Namespaces

One assembly, four namespaces, and they do not reach upwards:

Namespace
AvaTerminalThe control, the built-in shell, the pty session, the font, and ConsoleSize, CommandLine, CommandResolver.
AvaTerminal.VtThe parser and the screen model: VtEngine, Screen, Row, Cell, Scrollback, VtColor.
AvaTerminal.SceneThe visual tree and the renderer's contract: Theme, Rgba, CellMetrics, ISceneContext, TerminalVisual, SceneGraph.
AvaTerminal.PtyThe kernel object: IPtyHost, PtyStartInfo, PtySignal, PtyException.

AvaTerminal.Scene is a namespace inside a type's own name. Where that is ambiguous — inside namespace AvaTerminal — qualify it as global::AvaTerminal.Scene.Theme, or add a using alias.
